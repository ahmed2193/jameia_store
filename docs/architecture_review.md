## Cross-cutting themes (seen in all five areas)

1. **No use-case layer.** Every reviewed feature collapsed its use cases; cubits call repositories directly, and business rules have leaked into cubits, repositories, datasources and widgets (§2, §4).
2. **Duplicated shared entities.** Features re-declare `ProductEntity`, `ShopEntity`, `JameiaOrderEntity`, `JameiaAddressEntity` … and their mappers instead of using `core/domain/entities` + `core/data/mappers`; some names collide with core (§4 Shared entities).
3. **DTOs as contracts.** Core DTOs (`Product`, `JameiaAddress`, `Shop`) still flow through domain repository contracts, cubits, route extras and pop results (§4 Data, §6).
4. **Business logic in UI.** Pricing/VAT/fees in widgets, validation rules duplicated in 5 places (address), map/Places/GPS calls from page `State`, pages without any cubit (`ShopPage`, `ShopMapPage`) (§7).
5. **Datasources doing too much.** Translated strings (`.tr()`), motion tokens, refund maths and invented demo data inside datasources that return domain aggregates (§4 Data).
6. **Silent failures.** Mutation results (`Either`) ignored; success UI shown regardless (orders refund/review).
7. **Cross-feature widget/cubit reuse** (shop SKU sheet used by product_details; PDP card copies home rail controls) that belongs in `core/`.
8. **Missing tests** for cubit/use-case/business logic in orders, address, shop, product_details.

## orders

### Architecture audit — FAIL (Poor)

The orders feature has the §1 folder layout, but most business logic sits in the wrong layer. There is no domain/usecases folder: all six cubits call a screen-shaped OrdersRepository. The feature declares its own copies of the shared order, order-item, rider and address entities and mappers, and adds a presentation/util helper that reads the global Intl locale. The local datasource builds a domain RefundDetail that already holds translated text and refund math. Pricing, tax and fee logic, order-status rules and form state are spread across widgets, and two screens each hold user input (review comment, refund preference) that is never submitted. Mutation results are swallowed, so failures would show as success, and the refund flow ignores which order it came from. The tracking and map screens repeat the same widgets and logic (two cancel sheets, one of them a no-op; two map implementations; two copies of PulseNode), and the feature has no tests. Wiring the real jm3eia API would mean rewriting the domain and data layers and changing many widgets.

### Clean-code review — FAIL (Concerning)

The orders feature follows the folder layout, but the domain and data layers do not work as the contract says. There is no domain/usecases folder: cubits call OrdersRepository directly. Business rules are spread across the datasource (refund maths, localized labels), the repository (active/history split), cubit state (refund amount) and widgets (invoice fee/VAT maths, line totals). The feature also re-declares OrderEntity, OrderItemEntity and RiderEntity and their mapper extensions, even though core/domain/entities and core/data/mappers already have them. It adds its own display extension instead of the core nameFor/shopNameFor selectors. Error handling is inconsistent: refund and review submits show success whatever the result, cancel failures are dropped silently, and the cancel sheet on the tracking screen never sends a cancel. The presentation layer has four god pages (730–945 lines) and a 413-line map State that runs its own timers. Widgets are copied within the feature (photo uploader, section cards, two MapAppRow classes, two cancel sheets, a PulseNode copy that brings back a documented dispose bug). ## product_details

### Architecture audit — FAIL (Concerning)

The PDP feature does not follow the clean-architecture layers yet. Its domain is built on the core `Product` DTO: the route extra, page, cubit, repository contract and `ProductDetail` aggregate all use it, even though `core/domain/entities/ProductEntity` already has every field the page needs. Because of that, home and search have to convert their entities back into DTOs just to open the page. There is no use-case layer. Recommendation and ranking rules sit in a production datasource named "Dummy", which returns the domain aggregate directly and makes up discounts, calories, storage, deals and recipe data for every real product. Pricing, variant and stock logic in `ProductDetailCubit` is a near-copy of `ShopSkuCubit`, with a third copy in `CartItem`. Section data is kept outside the cubit state, and the cubit reads another feature's repository and is also told about VIP changes through a listener, so VIP has two sources of truth. UI parts are copied from home, shop and discovery instead of shared, and the tests are one widget smoke test plus router cases.

**Lints:** architecture_lints baseline has 126 diagnostics in product_details: no_magic_ui_values 67, one_widget_per_file 38 (product_detail_page.dart alone holds 17 extra widget classes in 909 lines; pdp_product_card.dart 7), presentation_no_data_layer 6 (core/data/models + catalog_constants in page/card/util, and domain repositories imported by the page), no_cross_feature_imports 5 (shop page `shopRouteArg`, cart `quick_add` widget, shop `product_sku_sheet` widget, store_mode repository in cubit and page), cubit_depends_on_usecases 4, domain_layer_purity 2 (entity + repository contract import core/data/models), no_service_locator_outside_di 2 (page resolves repositories), repository_impl_uses_base_mixin 1, feature_structure 1 (presentation/util). By count, the debt is mostly UI tokens and multi-widget files. The structural rules (domain→DTO, cubit→repository, no mixin, cross-feature widget and repository imports) show that the §4 layer model has not been applied to this feature at all. They are symptoms of the judgement findings below and are not listed again.
